## Prioritized concrete defects

There are no P0/P1 or approval-blocking findings in the inspected scope. The following P3 findings are concrete static control-flow findings, not executed reproductions.

### P3 — A byte-identical source-pin update leaves receipt and lock provenance inconsistent

**Locations:** `lib/catalog.py:549–557`, `lib/harness.py:384–390`, `lib/harness.py:418–420`, `lib/harness.py:431–441`. Related coverage: `tests/test_harness.py:470–489`.

**Trigger:** Install an upstream project skill at source commit A. Update its catalog source to commit B while the selected installed payload bytes and executable contract remain identical. This occurs naturally when a source repository changes outside the selected skill. A changed original payload that adapts to the same installed bytes is another case.

**Behavior and consequence:** `check_destination` returns unchanged based on ID, current installed hash and executable contract, without comparing source provenance. Sync skips preparation and installation for that job, so its `.skill-catalog.json` receipt still names A. It nevertheless writes a lock constructed from the current registry, naming B. A subsequent clean status can therefore accompany two different source commits for the same installed selection. Content integrity is still protected by the installed hash; the defect is an ambiguous audit/provenance result, not demonstrated execution of altered code. The existing provenance-update test changes the payload as well as the pin and does not cover this edge.

**Smallest remedy:** Define and preserve the distinction between original installation provenance and current catalog compatibility. Either expose both explicitly, or introduce a metadata reconciliation path for provenance-only updates while retaining existing ownership/change checks. Do not simply relabel the receipt as freshly fetched from B if no source fetch/verification occurred.

**Meaningful check:** Install A, change only the pin to B, then plan/sync/doctor. Assert a clear, consistent provenance result without rewriting skill contents or falsely asserting a fetch. Also cover changed source/adaptation metadata with identical installed bytes, user-edited receipts/payloads and unchanged-repeat behavior.

### P3 — Global skill export includes generated Python cache payloads

**Locations:** `lib/catalog.py:179–184`, `lib/bundle.py:162–171`, `lib/bundle.py:243–249`; ordinary cache-producing import at `skills/skill-catalog/scripts/harness.py:6`. Contrast the explicit snapshot exclusions in `lib/bundle.py:90–97`.

**Trigger:** Invoke the installed/source `skill-catalog` harness wrapper using ordinary Python bytecode settings in a writable checkout, or otherwise leave `scripts/__pycache__/catalog.*.pyc` under an authored global skill. Then export the global bundle.

**Behavior and consequence:** The wrapper imports sibling `catalog.py`. `read_local` walks every file beneath the skill directory without excluding generated caches. For a global skill, `bundle.prepare` derives a source hash from that entire local set, and the export includes it. The embedded `_harness` snapshot excludes bytecode, but the separately exported `skills/skill-catalog` payload does not. Identical authored sources can thus yield different payloads/provenance depending on prior wrapper use, Python version and local compiled-file metadata. This is a reproducibility and payload-hygiene defect, not evidence of an exploitable security issue. The inspected bundle test places a cache under `lib`; that exercises snapshot filtering, not a cache inside a global skill.

**Smallest remedy:** Apply an explicit generated-file exclusion policy to authored global export payloads, consistent with snapshot/global synchronization behavior. Preserve strict reviewed-byte handling for upstream payloads rather than silently weakening all catalog hash contracts.

**Meaningful check:** Add cache files under the authored global skill's `scripts/__pycache__`, export before and after, and require identical authored payload/provenance with no `.pyc`/`.pyo` files. Keep coverage that real scripts, references, licenses, executable declarations and the embedded locator are retained.
