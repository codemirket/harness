# Technical documentation

Identify the reader, task, prerequisites and authoritative implementation/source. Inspect the current behavior and adjacent documentation before writing. Distinguish implemented product behavior from proposed, historical and platform-specific material.

Organize around the task and decisions a reader must make. Keep ownership, units, defaults, errors and recovery explicit where they change use. Use minimal accurate examples and preserve identifiers/source identity. Do not copy restricted upstream documentation or treat a reference as a new dependency.

Run changed commands/examples in a safe authorized environment, verify links and check the actual interface/API names. Label unrun examples and unavailable platform paths. For substantial structure changes, verify that a reader can find prerequisites, execute the task and interpret a failure.

Return the edited source, verification evidence and known gaps. Stop when the requested reader task is accurately documented and checks pass. Do not present proposals as shipped features or publish external docs without authorization.
