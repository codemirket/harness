# Interface composition

Inspect the existing product, supplied target and real content before composing. Establish the primary user task, reading/action hierarchy, viewport range and required states. Identify the route, component, token, font, copy and asset owners that remain in scope, and state the files or artifacts to change; honor an already authorized scope and ask only when a new destructive expansion is ambiguous. Use an inspected target suited to the medium: reference image, minimal DOM, vector specimen or editable design source.

Compose spacing, type, color, grouping and assets around actual information. Reuse the project's design language when present; add visual variation only when it serves meaning. Include meaningful empty, loading, error, success, selected and disabled states. For a single interactive component, also exercise default, hover, focus-visible and active states, or record why a state is inapplicable. Keep interaction semantics, keyboard order and focus visible as the layout changes.

Choose the composition for the task. An application screen needs clear navigation, current context, object state and a predictable place for actions. A public page needs a convincing opening and a reading sequence that leads to the requested action. Where a section makes factual or promotional claims, map them to supplied or verified proof; label a placeholder or revise an unsupported claim rather than inventing evidence. Navigation, forms, pricing mechanics and other useful sections need no artificial claim-and-proof structure. Decide the information density from real content and frequency of use. Repeated cards, oversized headings or large empty regions need a content reason; none is a default visual identity.

Set a small hierarchy of type, space, surfaces and emphasis, then inspect their relationships as a whole. Give the main action priority without making every section compete for it. Let long labels, missing images, large values and repeated rows pressure the layout before propagation. Define which regions wrap, stack, scroll or change order; preserve useful information and reading/focus order when they do. Avoid hiding overflow to disguise an unresolved layout.

Implement with project-owned code and Mirket design tools and the admitted Playwright MCP peer or installed project browser tests where used. Freeze an initial rendered specimen, then compare production against it for composition, wrapping, asset loading and responsive behavior. Check at a narrow size that pressures content and a wider size that exposes spacing decisions.

Exercise the important controls in their real journey: a filter changes results, a save action reports its outcome, and a dialog closes with focus in a useful place. Inspect settled and transient states with the content and viewport recorded. Retain matched before/after evidence for a revision; repair the owning layout or component rule and inspect other affected instances. A pleasant isolated component does not establish the screen's task hierarchy.

Use an accepted reference directly. If a composition question remains, the approved pinned [Hallmark](https://github.com/Nutlope/hallmark/tree/13ac0ec7e148655948100b6396439e481361d690) and [Emil](https://github.com/emilkowalski/skills/tree/e8a175de22ae1e49370fc144c1f3bb9aeedf988d) sources are optional comparison locators. Inspect only the relevant portion; their presence authorizes no copying, dependency or tool execution.

Return the saved source/artifact, inspected states/viewports, claim/proof notes when relevant and remaining defects. Unless the task sets another budget, share 30 minutes and three final repairs across interface production and review; combined motion work uses 45 minutes/four. Allow one target repair and do not restart the budget for another screen or specimen. Stop after required behavior and visual evidence pass or report the precise missing capability, asset or unresolved defect. Do not claim completion from a source diff or screenshot alone.
