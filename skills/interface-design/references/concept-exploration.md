# Explore the decision that is still open

Use when a meaningful organizing choice remains unsettled and a small comparison
can reduce its uncertainty. Preserve an accepted direction. A routine component
repair, requested style refinement or known usability fix does not need competing
concepts or another planning document.

## Make alternatives informative

Name the user problem and the decision to resolve. Define comparison criteria
before judging options, using the brief, constraints and observed task needs.
Separate hard thresholds from tradeoffs: required recoverability may disqualify
an option, while scanning effort or implementation cost can be weighed. Thresholds
need a real basis; do not invent step counts, item limits or timing rules to make
a preference appear objective.

Change a meaningful organizing idea: the sequence of user actions, the unit of
interaction (one item versus a batch), the division of work between person and
system, the entry point, or when the user commits. Different colors around the
same sequence do not test a different interaction hypothesis. Each alternative
should be a credible solution with a named assumption it tests; omit padding and
deliberately weak options.

Hold fidelity, fixture content, theme and available effort comparable. Choose
the cheapest representation that exposes the decision: annotated sequences may
answer an order question, while focus or drag behavior needs a working specimen.
Do not compare a polished interactive option against a rough sketch and attribute
the preference to its underlying idea. Shared fixtures need not imply identical
flows: different action sequences are often the variable under test.

## Choose and preserve the learning

Apply the same criteria to the incumbent and alternatives. Explain the evidence
for each conclusion and distinguish observed results from predictions. A hard
threshold cannot be averaged away by high scores elsewhere. If options trade
different benefits, identify the priority or missing evidence that decides them.
Continue authorized work where the brief already resolves that priority.

State what the selected direction costs and what could overturn the decision.
For rejected concepts, keep their tested assumption, reason for rejection and
evidence that would revive them in the existing task record. Keep useful specimens
retrievable rather than maintaining a new catalogue of alternatives.

A hybrid is a new hypothesis. Explain why its combined sequence should work and
evaluate its own costs, state transitions and criteria; it does not inherit the
parents' evidence automatically. Neither votes nor an agent's score establish
human acceptance or measured usability improvement.

## Small worked comparison

Fictional brief: an administrator reviews requested access changes. Before making
specimens, define a hard threshold that no change is submitted without a review
and a way back; weigh review effort, visibility of exceptions and implementation
cost as tradeoffs. Use the same six sample requests, labels and visual primitives.

- **Per-request review:** inspect and confirm each request. Tests whether local
  context helps people notice exceptional permissions; costs repeated actions.
- **Batch summary:** scan all six, expand exceptions and confirm the batch. Tests
  whether comparison aids review; risks hiding per-request detail.

Give both the same two states—review and confirmation—with cancellation and
keyboard paths. A storyboard can compare ordering; working specimens are needed
before claiming that focus or exception discovery works. Suppose source constraints
show that batch submission cannot report partial failures. That is a concrete
cost to resolve, not proof that batches are universally worse. Select per-request
review if recoverability requires it, retain the batch concept's comparison
hypothesis, and record that reliable partial-result handling could revive it.
