# Brief to proof

Use this for substantial interface work. Scale the record to the change: a small
repair may need one sentence, one exercised state and one inspected capture.

## Ground the direction

Recover what the brief already answers before asking anything. Identify the
person, task, setting, main decision or action, content, platform and constraints.
Read the existing implementation and representative real data when available.
Separate supplied facts, observed behavior, reasonable assumptions and unknowns.
Numbers, testimonials, prices and dates are claims; keep them verified or visibly
label them as sample content. Never make invented content look credible by adding
precision, logos, named customers or a fabricated history.

Describe the intended experience in terms that guide decisions: for example,
"compare three offers without losing cancellation terms" rather than "premium."
Note what must stay consistent with the product and what this task may change.
If references are supplied, identify their relevant traits and limitations. A
screenshot shows appearance at one moment; it does not establish behavior,
responsive rules, font identity or rights to reuse its assets.

## Compose from the information

Order content around the user's decision. List the essential information, its
relationship and the next action before arranging boxes. Use these relationships
to choose grouping, alignment, reading order, density and emphasis. A comparison,
narrative, task list and exploration view should not automatically share a layout.

Make one clear hierarchy with supporting levels. Test it using the actual copy
and asset proportions. Use space, scale, contrast, position and type together;
one oversized heading cannot repair a confused information structure. Let the
content justify repetition and variation across sections. Neither identical card
grids nor compulsory asymmetry are universal solutions.

Use the product's tokens and components, or define the smallest coherent set
needed for a new direction. Choose typography for language coverage, readability
and tone. Establish image purpose, crop, focal point and relationship to text.
Evaluate a specimen at the intended size before extending a costly direction.
Alternatives should change a meaningful organizing idea, not merely the color.
Existing approval or a sufficiently clear brief is enough to continue.

## Derive the state and device matrix

Include the states the actual interaction or data contract can reach. Record
unsupported cases as gaps, not implemented behavior. Use a compact matrix in the
existing task record when several dimensions interact:

| Dimension | Select cases from the actual task |
| --- | --- |
| Journey | Entry, main action, cancellation/back, completion and recovery |
| Data | Normal, zero/one/many, missing optional content, long text, large values |
| Async | Initial load, pending mutation, partial result, failure, retry and stale data |
| Access | Keyboard and focus, touch, pointer, permissions and unavailable actions |
| Layout | Intended wide/narrow sizes, constrained container, enlargement and orientation |
| Locale | Relevant writing direction, expanded translation, numbers and dates |
| Motion | Reduced motion, rapid repeat, reversal and interruption |

Do not multiply every row into an exhaustive Cartesian product. Choose cases
that can expose a distinct failure. Keep plausible fixtures at the data boundary;
do not alter markup to manufacture a failure. Test native controls and established
accessible primitives before inventing interaction machinery. Disabled, loading,
validation and focus behavior must follow the control's actual semantics.

For mobile work, inspect keyboard obstruction, safe areas, scroll restoration,
back navigation and the ability to reach the primary action. A phone-sized
browser screenshot does not prove native platform behavior. Distinguish browser
emulation, simulator/emulator and physical-device evidence.

## Inspect, repair and prove

Run the working screen. First complete the user's main task; then inspect the
chosen matrix cases. Inspect the full composition at use size and focal areas in
detail: hierarchy, wrapping, grouping, alignment, color, image quality, text
legibility and states. Check motion in playback as well as intermediate frames.
Use applicable accessibility checks; a stylistic preference is not a conformance
rule, and one contrast formula does not substitute for another standard.

Write defects as observations with a location and effect: "The price wraps below
its unit at the narrow card width, making two offers hard to compare." Repair the
cause and reinspect the same scenario, plus directly affected neighbors. Avoid
unrelated restyling during a correctness repair. Prefer one meaningful iteration
over repeated ungrounded aesthetic scoring.

Retain enough evidence to identify the inspected result: source revision or
changed files, route/artifact, scenario/data, viewport/device, and relevant theme
or motion setting. Link captures where useful. Recheck after changes to inputs
that affect those results. A saved screenshot proves capture; an inspection
record explains what was judged and what remains uncertain.

For larger work, give a fresh reviewer the brief, working artifact, chosen cases
and evidence. Ask for located defects before sharing the maker's self-assessment.
Resolve consequential findings and record limits. Deliver the working result
and a concise evidence statement. Keep user approval, functional verification
and visual inspection separate; never invent acceptance.
