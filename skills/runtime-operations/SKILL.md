# Runtime operations

Select the operation from the requested outcome and explicit project scope. For a qualified Mirket-owned operation, use Mirket first. Inspect the running runtime's release identity and the specific platform capability after setup, reconnect, a relevant failure or a changed installation. Reuse verified readiness while its inputs remain unchanged. Installation, registered paths, process startup and a useful result establish different facts.

Read the actual available operation schema; do not invent a tool name or treat this skill as an execution API. Select an explicit absolute `project_root` where required. Resolve supported project-relative file paths against that root, not the tool process working directory; follow fields requiring absolute paths and preserve fields defined as relative, including video asset/caption paths. Path selection does not grant host permission. Use mirket setup, mirket doctor and mirket update for their owning installation tasks. Passive inspection does not authorize a runtime probe, update or project-file synchronization. Codex owns general browsing, SQL work, agents, permissions, editing, shell and Git; a Mirket process is not a sandbox.

Bind writes and jobs to the source/destination revisions and operation identity required by the API. After response loss or cancellation, inspect the original operation, receipt and actual destination before replaying anything. A missing receipt does not prove no effect occurred. Stop dependent effects when readiness, ownership or effect knowledge is unresolved; name the exact unavailable capability and continue independent authorized work.

Return the observed release/platform, selected scope, actual result and verification limits. A healthy doctor result alone does not establish client activation or artifact correctness.
