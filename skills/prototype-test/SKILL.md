# Prototype test

Identify the riskiest assumption and the observation that would support or reject it. Choose the smallest faithful prototype that can elicit that observation: content, interaction, layout or technical slice. Preserve real task constraints without pretending a simulation is production behavior.

Define participant/context, task, success/failure evidence and decision rule before observing. Use existing authorized participants or supplied research; recruitment/outreach needs its own authorization. Avoid leading tasks and separate observed behavior from participant explanations and your inference.

Build and inspect the prototype using appropriate host/design tools. Use established project browser tests/tools for interactive journeys. The optional Pi peer can supplement local `127.0.0.1` reduced-motion screenshots and limited navigation-key checks, but exposes no pointer click or text entry; keys may still activate local controls. Report missing live browser capability when required. Run the bounded task, retain relevant evidence and note fidelity/sample limits. A polished artifact or positive opinion alone does not validate task success or demand.

Return the prototype, task, observations, decision and remaining uncertainty. Stop when the assumption is discriminated to the agreed confidence or the test cannot observe it. Do not expand into full production or claim validation from an unrun test plan.
