# Design critique

Inspect the actual target at its intended size and in the states relevant to the user task. Use Codex's available browser for live web targets. Capture the current evidence before editing; distinguish a reproducible usability defect from a subjective preference.

Evaluate task hierarchy, content density, alignment, typography, spacing, contrast, assets, controls and responsive behavior as one composition. For public-facing claims, treat absent or unsupported proof as a content-truth finding when observed, not as a visual preference. Identify the small set of changes with the greatest effect on comprehension or use. Explain each issue by what the user misses, misunderstands or cannot do, using a precise location/state.

Locate the weakest relationship before selecting a treatment: competing headings can obscure the action; equal spacing can hide grouping; a busy image can overpower its caption; a disabled state can resemble a selected one. Trace the observed problem to the responsible content, layout, style or interaction owner. Rank by blocked task, mistaken interpretation, reading effort and then craft refinement. Do not present personal taste as a functional defect.

For each material finding retain the view/state, observed symptom, user consequence and a concrete repair in paired before/after evidence. When a baseline or diagnostic can distinguish pre-existing, introduced and unknown findings, preserve that attribution; a clean detector result is evidence, not proof of visual or accessibility quality. State uncertainty when a claim would need task observation or assistive technology that was unavailable. An unconventional composition may be intentional; judge whether its information and controls remain understandable before normalizing it.

For a high-risk or matched review, read [references/review-packet.md](references/review-packet.md). It records the exact source revision, intended loaded route/state, viewport/theme/content, saved-pixel inspection versus structural checks, ranked findings and frozen expected outcome. Use it to preserve the best verified candidate and one shared task repair budget; do not treat a new specimen or delegate as a budget reset.

Keep the existing product direction and authorized file/component scope unless the brief authorizes a new one. Make focused repairs, then inspect the same views and states for regression. Check whether a local improvement worsens nearby hierarchy, consistency or access.

Match content, viewport, theme, zoom and state when comparing. A pixel diff can reveal changed regions but cannot decide whether a change improves use. Inspect the full result and any affected responsive layout, then report any loss along with the gain. An independent reviewer, when useful and available, should see the rendered artifact and task rather than only the implementation's explanation.

The approved pinned [Impeccable](https://github.com/pbakaus/impeccable/tree/4e8504f10106a1cd7a99e37a401aa368d1d55576) and [Design Anatomy](https://github.com/wheresryan22/anatomy/tree/1482e8469b0a9e0d8cc18ea2740a01423d29ae80) sources are optional comparison locators for a specific unresolved craft question. They do not establish a universal style rule or rights to adopt their material.

Return ranked findings, the repaired source when requested, and paired evidence showing what changed. Unless the task sets another budget, share 15 minutes/two final repairs for static work, 30 minutes/three for interfaces or paged work, and 45 minutes/four for motion across production and critique; use the largest applicable limit. Report unresolved issues at the limit. Avoid an endless polish loop or a checklist that invents defects in already effective design.
