# Open-source toolchain proposal

**Historical component shortlist.** [Decisions 84–93](decisions.md#decision-84--simplification-review-first-revision) replace the document/OCR, broad language-analyzer and guide-delivery directions in this 2026-10-24 proposal, while restoring private Chromium, strong design and HyperFrames video in a narrower Codex-only topology. The [revised plan](implementation-plan.md) owns current scope; this note is source research and admits no dependency.

Use the [proposed consolidated implementation plan](implementation-plan.md) for the current dependency boundary, execution order and acceptance. This document preserves component evidence from the older M0/M3/M5 structure; [decision 79](decisions.md#decision-79--host-owned-office-workflows) changed Office execution ownership, and later decisions narrowed or restored the remaining release surface.

Research snapshot: **2026-10-24**, with Office ownership updated under decision 79. The original review established component direction, not runtime verification or a completed dependency audit. Historical research statements below retain their original evidence scope; current dependency admissions and implementation evidence live in the owning admission and qualification documents.

## Recommendation

Keep the agreed Rust core, private Node.js LTS adapters and host-owned agents. Package selected Mirket-managed specialist engines privately, launch them on demand, and give each capability one primary implementation. Office creation, editing, recalculation, rendering and export use the available Codex host tools under decision 79; Mirket supplies guidance, workflow and verification, without a bundled Office engine or an identical self-contained Office guarantee. Prefer an existing narrow library or executable over another agent framework, server stack or custom implementation.

The material changes to the earlier shortlist are:

1. **Recommend HyperFrames instead of Remotion for authored video**, using locally packaged Anime.js/CSS/WAAPI compositions and a controlled FFmpeg build. Its documented Node/headless/export interfaces fit this harness better than Motion Canvas's editor-oriented rendering path. Verify the exact package before admission; the project is still young.
2. **Do not replace Sharp or OpenPencil with PhotoCraft.** PhotoCraft addresses layered photo editing, while these tools own image processing and interface design. Its maintainers explicitly call it early alpha. Keep it as an evaluated alternative, not a default dependency.
3. **Prefer TypeScript 7's upstream native LSP for ordinary JS/TS navigation**, removing the extra `typescript-language-server` wrapper if its fixtures pass. Framework language servers remain responsible for Vue/Angular/Astro; compatibility must be checked independently.
4. **Use only decision 81's exclusive language targets, plus the retained SQL dialects.** Keep syntax/structure and original positions distinct from full navigation; removed-language analyzers are not release dependencies or qualification gates.
5. **Keep the mature document baseline, but evaluate a concrete simplification:** Docling's narrowly selected Python pipeline versus `docling.rs`. Xberg (formerly Kreuzberg) is a secondary challenger. Ship one winner; do not ship several document-intelligence frameworks as fallback layers.
6. **Keep SQLite-based memory and Playwright-based browsing.** Do not add a vector database service, browser agent, graph service or general crawler merely because it is popular.

Install under the user's home `.mirket` using platform installer scripts and a maintained installation prompt. Prefer thin shell/PowerShell bootstraps handing off to the Rust `mirket setup` owner; keep shared installation/update logic out of prompts and duplicate scripts. Mirket-managed payloads remain complete and platform-specific, with no global runtime fallback. Office tools remain host-provided under decision 79 rather than part of that payload. Archive, bootstrap trust, native signing and activation mechanisms still need qualification; a script is not an exemption from those requirements.

Decision 69 brings native Windows into the first release alongside macOS Apple Silicon. Decision 70 selects Windows 11 x64 and ARM64; exact supported Windows builds remain to be qualified. No WSL/VM dependency, global managed-tool fallback or separate Windows orchestration/installation stack is selected. Shared Rust/TypeScript source alone is not runtime evidence. Apple SDK functionality remains Apple-specific; platform SDK-dependent C/C++ navigation requires separate qualification.

Decision 71 selects native-first Windows ARM64 with documented, privately packaged and tested x64 helper-process exceptions when a suitable native build is unavailable. Microsoft documents built-in Windows 11 emulation for x64 user-mode applications. The accepted policy permits this route for explicitly selected helper processes; it is not evidence that arbitrary tools work or permission to mix incompatible native libraries in one process. Keep the Mirket core native; qualify architecture-compatible dependencies per process and test each selected exception’s actual output, performance, cancellation and update behavior on Windows ARM64. Record architecture, rationale, private dependencies and verification in the release inventory; do not ship redundant emulated/native fallback implementations. ## Free/open-source selection rule

The user requested free, open-source tools. For the proposed shipped runtime, require usable source and an open-source license, with no mandatory vendor account, paid runtime subscription, per-seat or per-render entitlement. Public-domain software such as SQLite also qualifies. Hosted services offered alongside an OSS tool are not part of this package.

This is **not an MIT-only policy**. MPL, LGPL, EPL and GPL components can be sensible choices when their distribution obligations are met. Prefer permissive libraries where capability and quality are comparable; do not discard a useful FFmpeg build just because it carries copyleft obligations. The new repository's own license is still a separate decision. [OSI's explanation](https://opensource.org/faq), [SQLite's public-domain dedication](https://www.sqlite.org/copyright.html).

Review software, model weights, fonts, codecs, templates and brand assets separately. A repository badge does not license every downloadable binary or asset. The accepted macOS/host-client topology remains: this proposal does not claim macOS, Apple SDKs or host-agent subscriptions are open source or free. Do not redistribute proprietary platform SDKs as if an analyzer's OSS license covered them. Decision 81 retains only selected C/C++ SDK prerequisites within the first-release language scope; no automatic installation or global developer-tool changes.

The retained A–G references remain unchanged. Remotion and GSAP may remain engineering references without being bundled runtime dependencies. Researching HyperFrames and PhotoCraft does not automatically add their entire skill catalogs or assets to the selected guidance catalog.

## HyperFrames: recommended video direction, with a narrow integration

**Evidence inspected:** repository metadata and README; release `v0.8.192` dated 2026-10-24; its LICENSE, engine/core/producer manifests, producer API, rendering guide, browser/FFmpeg path handling, Anime.js adapter and regression fixture, and telemetry policy. The public repository was created on 2026-03-10: active release work is evident, but it is not a long-established runtime. [Release](https://github.com/heygen-com/hyperframes/releases/tag/v0.8.192), [license](https://github.com/heygen-com/hyperframes/blob/v0.8.192/LICENSE).

The producer exposes a programmatic render-job API and documents MP4, WebM, GIF and PNG sequences, plus supplied-media audio mixing. That is a substantially closer fit than adapting an interactive editor into our render engine. Its released packages target Node 22+, even though upstream develops with Bun; Mirket need not adopt Bun as a runtime. [Producer API](https://github.com/heygen-com/hyperframes/blob/v0.8.192/packages/producer/README.md), [engine manifest](https://github.com/heygen-com/hyperframes/blob/v0.8.192/packages/engine/package.json), [render formats](https://github.com/heygen-com/hyperframes/blob/v0.8.192/docs/guides/rendering.mdx).

Use the producer/engine API through our TypeScript adapter. Do not install the complete upstream agent plugin, cloud renderer, media-generation services or skill updater. The core currently depends on studio-server utilities; a library integration is not proof that all studio-related code disappears from the dependency closure. Resolve the published artifacts rather than guessing from package names. [Core manifest](https://github.com/heygen-com/hyperframes/blob/v0.8.192/packages/core/package.json).

**Use Anime.js/CSS/WAAPI compositions, not the default GSAP-oriented examples.** The source contains a v4 Anime.js adapter and a rendered regression fixture. The adapter requires instances to be registered and sought explicitly; a plausible animation that remains static during export is a discriminating failure case. Keep scripts/fonts/assets local. Check the assembled runtime, generators and chosen templates for implicit GSAP/CDN injection rather than assuming omission from the npm manifest is sufficient. [Adapter](https://github.com/heygen-com/hyperframes/blob/v0.8.192/packages/core/src/runtime/adapters/animejs.ts), [fixture](https://github.com/heygen-com/hyperframes/blob/v0.8.192/packages/producer/tests/animejs-adapter/meta.json), [Anime.js license](https://github.com/juliangarnier/anime/blob/master/LICENSE.md).

GSAP's package declares its own Standard No Charge license; free pricing is not the OSS licensing criterion selected here. The current license webpage redirected to a temporary-offline page during this review, so this assessment does not claim a complete fresh interpretation of those terms. Exclude it from the default bundle on the established license-category distinction. [Package declaration](https://github.com/greensock/GSAP/blob/master/package.json).

Private packaging must explicitly supply the browser and media paths. The engine otherwise searches shared caches or falls back to executable lookup. Reusing the Playwright Chromium binary is a **testable optimization**, not an established compatibility fact: Puppeteer/CDP and HyperFrames capture behavior must both work. If not, account for a separate private rendering browser; never use personal Chrome. The upstream CLI also has telemetry controls; prefer the narrow library path and disable/verify any telemetry surfaces that remain. Decision 53 requires local-only diagnostics and no automatic reporting across the assembled toolchain; CLI flags alone do not establish compliance. [Browser resolution](https://github.com/heygen-com/hyperframes/blob/v0.8.192/packages/engine/src/services/browserManager.ts), [FFmpeg resolution](https://github.com/heygen-com/hyperframes/blob/v0.8.192/packages/engine/src/utils/ffmpegBinaries.ts), [telemetry policy](https://github.com/heygen-com/hyperframes/blob/v0.8.192/packages/cli/src/telemetry/policy.ts).

Readiness requires actual audio sync, alpha, captions, local fonts, all four agreed formats, cancellation and two-job tests on the reference Mac. SRT/WebVTT sidecars can be serialized from the agreed supplied caption text/times; no transcription model is implied. Determinism means repeatable content/timing under a pinned environment, not an untested byte-identical MP4 guarantee across hardware. Do not infer performance superiority from the project's popularity.

**Alternatives:** Remotion fails the requested default licensing category; retain it as a reference. Motion Canvas is MIT and established longer, but its documented rendering workflow and an open upstream headless-use issue leave more integration work for this harness. Blender is a mature OSS choice for a different 3D/compositing authoring problem, not an automatic replacement for DOM-based motion. Do not bundle multiple video frameworks. [Remotion FAQ](https://www.remotion.dev/docs/license/faq), [Motion Canvas rendering](https://motioncanvas.io/docs/rendering/), [headless issue](https://github.com/motion-canvas/motion-canvas/issues/1218).

## PhotoCraft: useful direction, not a foundation replacement

**Evidence inspected:** repository metadata, README, Cargo manifest, releases including `v0.15.1` dated 2026-10-23, source license and separate brand license, plus the maintainer's parity assessment. The repository was created on 2026-09-30; this records public-repository age, not proof that all development began that day. [Repository](https://github.com/storytold/photocraft), [release](https://github.com/storytold/photocraft/releases/tag/v0.15.1).

PhotoCraft is a Rust layered-image editor with a headless CLI, command engine, native documents and PSD support. Its software is MIT OR Apache-2.0. These are real architectural advantages for automation. However, the maintainers explicitly describe it as early alpha and distinguish implemented menu commands from professional readiness. Their parity report contains older measurements alongside newer updates, so its percentages are not a current independent benchmark. [README and limitations](https://github.com/storytold/photocraft/blob/v0.15.1/README.md), [parity assessment](https://github.com/storytold/photocraft/blob/main/docs/target-app-parity.md), [license](https://github.com/storytold/photocraft/blob/v0.15.1/LICENSE-MIT).

It does not replace OpenPencil's interface/component/layout workflow. It also does not justify replacing the narrower Sharp/libvips batch pipeline: its documented AVIF support is optional and write-only, while AVIF is already part of our agreed output scope. Claims about Rust or GPU acceleration do not establish lower total latency for our tasks.

**Recommendation: leave PhotoCraft out of the baseline package.** If editable photographic retouching/PSD work becomes an explicit requirement, compare it against GIMP on that task. GIMP is the maturity-first candidate with documented batch operation; its GTK/GEGL/Python closure and private configuration still cost something. Do not add both editors merely to cover uncertainty. [GIMP CLI](https://www.gimp.org/man/gimp.html), [GIMP license](https://github.com/GNOME/gimp/blob/master/COPYING).

PhotoCraft's brand assets are explicitly outside its software licenses. That does not invalidate its OSS code, but a modified/repackaged distribution needs correct attribution and branding treatment. [Brand terms](https://github.com/storytold/photocraft/blob/v0.15.1/docs/brand/LICENSE-brand.txt).

## Documents: quality baseline and the best simplification opportunity

Decision 59 sets a common adapter save contract for edited documents/designs: new output copy by default; explicit in-place instructions honored without repeated confirmation. Qualify staging/finalization, concurrent-change detection and linked-asset preservation with the selected engines so partial results cannot replace existing files.

**Baseline recommendation:** host Codex tools for Office creation/editing/recalculation/rendering/export, Typst for authored PDFs, pypdf/PDFium for defined PDF operations, and Docling with a deliberately selected set of format/model/OCR features. Decision 54 selects English, Turkish, German, French, Spanish, Italian and Portuguese OCR, including representative mixed-language documents. Bundle the required local language assets; exact versions, licenses, recognition quality and footprint remain to be verified.

Current Docling packaging distinguishes `docling-slim` extras. Build a resolved subset for the actual PDF and document-extraction workload rather than installing every optional VLM, speech, service-client and enrichment dependency. Selecting a slim package name alone does not remove PyTorch from the standard local layout/table path. The inspected manifest still includes local model/runtime dependencies. [Manifest](https://github.com/docling-project/docling/blob/main/pyproject.toml), [OCR options](https://docling-project.github.io/docling/getting_started/installation/), [local model configuration](https://docling-project.github.io/docling/reference/pipeline_options/).

Use explicit local artifacts and disable remote services and unselected plugins. Docling model assets have their own license declarations, including Apache-2.0 and CDLA-Permissive-2.0 in the inspected model repository; a final model list must identify which terms apply to each file. Do not assume the Python package's MIT license covers weights. [Model card](https://huggingface.co/docling-project/docling-models/raw/main/README.md).

**Best challenger: docling.rs.** It is an MIT Rust implementation using ONNX with a pure-Rust PDF renderer by default at the inspected tag; PDFium is opt-in. Its published conformance run uses the docling-parse renderer with OCR disabled and specific model inputs, so those results cannot be assigned to the default multilingual pipeline. The inspected release is `v2.51.1` (2026-10-24). Upstream publishes conformance tests and performance comparisons, but the project is young and its PDF ML path is not universally byte-identical to Python Docling. Its own-groundtruth comparisons are evidence of compatibility, not independent proof of best document accuracy. Evaluate it on the same English/Turkish scans, merged-cell tables, reading order and source-coordinate fixtures. [Release](https://github.com/docling-project/docling.rs/releases/tag/v2.51.1), [migration/conformance limits](https://github.com/docling-project/docling.rs/blob/v2.51.1/docs/MIGRATION.md), [tagged conformance methodology](https://github.com/docling-project/docling.rs/blob/v2.51.1/docs/PDF_CONFORMANCE.md).

Run one bounded M0b comparison against the selected narrow Python pipeline on identical required fixtures across all three targets. Promote docling.rs only if it preserves required extraction outcomes and demonstrates a meaningful whole-process resource/packaging benefit; Mac-only improvement is insufficient. Then remove the displaced Python extraction stack; do not preserve a compatibility layer or hidden fallback. This would not automatically remove the general Python needed by retained pypdf and SQL operations. Keep one general interpreter per target where needed, and account for its remaining consumers before claiming a Python-free package.

**Secondary challenger: Xberg**, formerly Kreuzberg. The repository redirect and current manifests were checked; older Kreuzberg 4.x documentation must not be treated as the API contract for Xberg 1.x. It is MIT, has Rust and Node paths and exposes feature selection for OCR/layout/ONNX. Its default/all-feature packages include many unrelated capabilities. A credible candidate must select only extraction/OCR/layout, omit providers/RAG/server/crawling/transcription, and audit model downloads and license closure. Do not make it a second memory system. [Current repository](https://github.com/xberg-io/xberg), [manifest](https://github.com/xberg-io/xberg/blob/main/crates/xberg/Cargo.toml), [release examined](https://github.com/xberg-io/xberg/releases/tag/v1.3.10).

OpenDataLoader's benchmark is useful disconfirming evidence: its hybrid and local modes differ substantially, so its headline score must not be assigned to the lightweight local deployment. Its PDF-only scope would still leave the Office extraction contract. [Project comparison and scope](https://github.com/opendataloader-project/opendataloader-pdf).

**Proposed integration contract:**

1. **Declare the schema context.** Select dialect, project query roots and canonical declarative schema files or a supplied schema snapshot. Parse supported `CREATE TABLE`/view declarations as data and retain their file/revision/spans. Multiple files may comprise one declared snapshot; duplicate/conflicting declarations are errors, not “last file wins.” Do not infer the currently deployed schema from arbitrary migration history. Migration-only projects can supply a current snapshot through their host-owned workflow; Mirket neither runs it nor creates a database. No new migration-state interpreter is proposed.
2. **Preserve namespace rules.** Treat PostgreSQL schemas/search-path context and SQLite namespace mappings as explicit analysis inputs where needed. Preserve quoted identifiers and dialect-specific case rules. Never assume a connection's environment, session settings, attached databases or credentials. Unqualified names with unresolved context remain ambiguous. A supplied snapshot is evidence of that snapshot, not of a live database's current state.
3. **Keep original positions separate from transformed SQL.** Parse original text, retain identifier identity and original spans, then qualify a copy for resolution. Normalized identifiers and expanded stars are not new source locations. A definition target must have a genuine declaration origin; a snapshot without source coordinates cannot yield an invented file location. Verify character/byte/UTF-16 conversions, inclusive token ends, CRLF and Unicode. SQLGlot stores token position metadata, but reliable mapping through transformations remains an adapter test obligation. [Parser](https://github.com/tobymao/sqlglot/blob/v30.24.0/sqlglot/parser.py), [position storage](https://github.com/tobymao/sqlglot/blob/v30.24.0/sqlglot/expressions/core.py).
4. **Build navigation from proven bindings.** Return the nearest relevant declaration for aliases/CTEs and the declared schema object for base tables/columns. Keep optional upstream lineage distinct from direct definition/reference relationships. Store reverse references in the existing checkout-scoped derived navigation cache, keyed by symbol, dialect, schema revision and source revision. Report the indexed scope and incomplete files; do not call a partial scan “all references.” Invalidate on schema edits, changed files and branch/worktree changes. No new database service, LSP daemon or parallel cache format is proposed.
5. **Bound execution and unknowns.** Use the existing on-demand helper lifecycle and privately packaged Python; SQL analysis must not import/start the ML document pipeline just to parse SQL. Use SQLGlot's parsing/qualification APIs, not its evaluator, SQL execution, model inference or HTML lineage visualization. Do not evaluate templates, ORM code, stored-procedure bodies or migration scripts. Dynamic SQL, unsupported constructs and missing schemas return partial/unsupported status, while any independently verified results retain their provenance. Embedded SQL requires a valid host-language source map; no guessed spans.
6. **Keep the adapter narrow.** Mirket owns schema selection/provenance, original-span mapping, result filtering, reverse indexing and lifecycle. SQLGlot owns dialect parsing and supported semantic qualification. Do not patch around unsupported semantics by accumulating a custom SQL resolver. Qualify common SELECT/JOIN/CTE/subquery cases first and check DML, views, recursive CTEs and dialect-specific features individually; parsing support is not evidence of navigation support. Report remaining gaps under decision 51 rather than silently promising complete SQL semantics.

## Memory: keep the architecture, avoid a fashionable service dependency

SQLite remains canonical; FTS5 and vectors produce candidates, and canonical scope/currentness/revisions determine eligible results. Decision 60 selects up to seven daily and four weekly memory recovery points plus pre-migration snapshots, bounded by a configurable storage cap and executed within the existing runtime. No missed-day snapshots or permanent backup service; forgetting applies to every managed snapshot. Decision 61 rotates oldest eligible backups at the cap, protecting the latest verified recovery point per scope and active-migration snapshots. If space is insufficient, report degraded backup coverage and defer migrations requiring a new backup while preserving ordinary memory use. Forgetting supersedes rotation protection. Decision 62 sets a configurable 5 GiB aggregate managed-backup default across projects/shared preferences, including migration snapshots; live memory, models, caches and project files are outside that budget. Decision 63 restores a user-selected recovery point into its selected memory scope, preserving recoverable current state first and applying known forgetting records; it does not merge automatically. Qualify temporary-space accounting, retention selection, atomic restore and migration recovery in M2 before release. Decision 64 preserves memory identity across verified workspace moves/renames, with ambiguous continuity requiring clarification and independent clones remaining separate. Decision 65 retains unavailable-project rebuildable indexes/caches for a 30-day grace period before eligible runtime cleanup, protecting durable and active state. Qualify identity evidence, availability checks and path/index revalidation without introducing a filesystem watcher or discovery service. Relationships and supersession do not require a graph database. Host-agent curation remains authoritative; do not add automatic LLM extraction or a transcript observer.

Keep sqlite-vec as the first exact-search candidate, statically controlled, with rebuildable embeddings. The upstream pre-v1 warning matters and release activity is less intense than the newly trending frameworks. That supports a conservative pin and correctness tests, not automatic rejection. SQLite's newer Vec1 is a credible alternative with exact and approximate modes, but its current 0.8 status and evolving filtering/index behavior do not make it automatically safer. Compare if sqlite-vec fails measured scale/correctness; do not ship both. [sqlite-vec](https://github.com/asg017/sqlite-vec), [MIT license](https://github.com/asg017/sqlite-vec/blob/main/LICENSE-MIT), [Apache license](https://github.com/asg017/sqlite-vec/blob/main/LICENSE-APACHE), [FTS5](https://www.sqlite.org/fts5.html), [Vec1](https://www.sqlite.org/vec1.html), [Vec1 exact/ANN behavior](https://www.sqlite.org/vec1doc.html).

Use local FastEmbed/ONNX assets and evaluate multilingual-e5-small on English–Turkish and exact code/path recall. Model-family support is not evidence that an arbitrary quantized artifact has the same quality or license. Compare one full-precision reference and one verified quantization, then package one winner. Keep embedding revisions atomic with index/currentness checks. [FastEmbed-rs](https://github.com/Anush008/fastembed-rs), [model source](https://huggingface.co/intfloat/multilingual-e5-small).

## Performance and packaging plan

The first dependency batch inventories the actual resolved runtime closure and distinguishes assembly-only tools. Record exact features/extras, native modules, assets, build/download steps and compressed/installed/staging bytes per target. For OpenPencil/HyperFrames, inspect published entry imports and transitive packages: a narrow library call does not prove that CLI, studio or desktop dependencies disappeared. Qualify Puppeteer browser provisioning explicitly; suppress incidental downloads, and share a compatible executable only after tests, never profiles. Sharp's platform optional packages must be assembled for the target rather than copied from one machine's node_modules. For FastEmbed, disable unneeded default/download/image features and select a compatible offline CPU ONNX closure; no runtime model hub. Docling feature names alone do not establish CPU-only inference: resolve all selected model backends and transitive ONNX/PyTorch packages. [Independent source evidence](reviews/2026-10-24/toolchain.md).

The distribution includes the selected Mirket-managed tools; Office execution is host-provided under decision 79. On-demand execution reduces idle RAM, not installed bytes. The large managed contributors remain the private Chromium build, language SDKs/runtimes and extraction models. “All written in Rust” would not eliminate these assets or guarantee lower memory.

Proposed launch shape:

- The host launches Mirket's Rust stdio process. Memory is local; model inference starts only when needed and unloads after the implementation plan’s bounded idle period or safe pressure-driven reclamation. Measure concurrent Codex sessions after semantic use.
- Browser sessions and language servers have explicit owners and bounded idle reuse. No permanent browser/agent broker is added.
- Mirket-managed design/extraction/PDF/video jobs use private inputs, profiles where applicable, output staging and child-process ownership. Stop only owned descendants. Host Office jobs use the host tool's lifecycle and permissions; report any unavailable cancellation or effect-inspection capability.
- A release-local tool inventory resolves every managed executable. No personal app, PATH executable, shared browser cache, automatic package installer or first-use model download fallback.
- Keep permitted web interaction separate from prepared local artifact rendering. Local authored renders must work with external networking unavailable; this is an application behavior test, not an OS-sandbox claim.
- Start the throughput experiment with **two heavy jobs** and bounded internal worker counts. This is a proposed measurement configuration, not an accepted or measured safe limit. Enforce aggregate capacity across simultaneous client processes without adding a permanent scheduler service.

FFmpeg should have a deliberate codec list. An OSS GPL-enabled executable with libx264 for compatible MP4 can be a logical choice; libvpx/Opus cover relevant WebM paths, subject to verified build/API support. Hardware encoding through macOS is optional and must preserve expected quality. [FFmpeg license/build distinctions](https://github.com/FFmpeg/FFmpeg/blob/master/LICENSE.md).

## Evidence quality, trends and remaining work

Research used upstream docs, source manifests/licenses, released source files, GitHub repository/release metadata, explicit maintainer limitations and available benchmark methods. Searches included headless/video alternatives, GSAP licensing, image benchmarks, document OCR/table alternatives, SQLite vector engines, native TypeScript LSP and the selected structural grammar candidates. This is a targeted engineering review, not an exhaustive market survey or a security scan.

The trends that actually affect selection are native upstream LSP adoption, Rust/ONNX document pipelines, HTML-native video engines and local embedded retrieval. Popularity and rapid commit counts are discovery signals. They do not establish stable releases, file fidelity, low memory, correct licenses or trustworthy benchmark comparisons.
