# Independent toolchain review — 2026-10-24

## Executive verdict

**Retain the architecture and most component choices; correct the PHP candidate and tighten the first qualification batch before freezing dependencies.** Rust plus private Node, separate Office-matched/general Python, SQLite, native specialist tools and host-owned agents remain a practical fit. Replacing that arrangement with an all-Rust mandate, a document/RAG platform, or an additional browser-agent framework would increase integration risk without demonstrated benefit.

The largest unresolved cost is the **complete language/runtime and document/model fleet**, not the Rust application. Launching it on demand reduces active resource use but does not eliminate release bytes, patching, provenance, architecture-specific dependencies or project-execution behavior. No scoped benchmark establishes that the assembled plan meets its 16 GiB reference configuration or idle-memory target.

The clearest new defect is Phpactor: its current upstream requirements prescribe WSL for Windows. A privately packaged x64 PHP interpreter does not solve that operating-system constraint. PHPantom 0.11.1 is a credible replacement candidate with released binaries for all three targets, but its automatic external-tool integration must itself pass passive-loading qualification. This is a targeted replacement investigation, not permission to ship two PHP servers.

For documents, keep LibreOffice/UNO and the accepted two-Python ownership. Compare the narrow Docling baseline with the already selected docling.rs challenger during M0, using identical quality requirements and explicitly fixed renderers/models. The existing description of docling.rs as a PDFium-based default is stale. Do not promote it based on headline speed or conformance figures.

**Evidence boundary:** read-only plan/source/release/registry research; no downloaded tools were executed, no dependencies installed, no models loaded, no upstream build scripts run, and no artifact/performance/platform results measured. All six plan files matched `baseline.json` at review entry. The new repository had untracked `planning/` and no `.mirket/project.json`. Only this report was written. Recommendations below are proposals, not dependency approvals.

## Prioritized findings

### T1 — P1: PHP's proposed Windows exception addresses the wrong incompatibility

**Plan locations:** `planning/platform-qualification.md:80`, `planning/implementation-plan.md:33`, `planning/implementation-plan.md:94`, `planning/toolchain-proposal.md:285`.

The matrix marks native Windows x64 PHP/Phpactor as `N/G` and proposes x64 PHP on ARM64. Current Phpactor documentation still prescribes WSL; its extension documentation independently states Linux/macOS support. This is an unresolved OS integration gap, not merely a missing ARM64 interpreter. Its maintainer also explicitly describes unresolved performance/accuracy/maintainability shortcomings. Do not spend the first slice privately packaging PHP before testing whether the selected server is admissible. [Phpactor](https://github.com/phpactor/phpactor), [extension platform warning](https://github.com/phpactor/vscode-phpactor).

PHPantom's 0.11.1 release is a concrete alternative, published 2026-10-07 with all three native artifacts. The release API reports archives of roughly 14.8–15.9 MB for those targets; these are **published compressed asset sizes**, not a measured installed closure or speed advantage. [Release metadata](https://api.github.com/repos/PHPantom-dev/phpantom_lsp/releases/tags/0.11.1).

However, do not replace one hidden-execution path with another: PHPantom detects external tools, accepts command overrides, and reloads project configuration. Its documented empty-command settings disable tools, but global configuration can be overridden by project configuration. The first experiment must establish an upstream-supported way to keep external execution disabled throughout the session, including reloads; no such non-overridable Mirket policy was established by this review. Its source-build script can download stubs; pre-stage the pinned stubs and use the offline build option, checking that it did not produce an empty stub index. [Configuration](https://github.com/PHPantom-dev/phpantom_lsp/blob/0.11.1/docs/configuration.md), [build script](https://github.com/PHPantom-dev/phpantom_lsp/blob/0.11.1/build.rs).

**Recommendation:** replace Phpactor's presumptive Windows feasibility with an explicit failed-source-support gate; evaluate PHPantom first for the single PHP owner. If passive loading cannot be achieved, return the precise conflict rather than create a server fork/custom resolver or silently weaken coverage.

### T2 — P1: Ruby needs an explicit M0 passive-loading gate

**Plan locations:** `planning/implementation-plan.md:117`, `planning/platform-qualification.md:79`, `planning/toolchain-proposal.md:284`.

M0 prioritizes Rust/C#/Java/Swift and generically mentions framework loaders, while Ruby is treated as a later runtime qualification. Ruby LSP's security document explicitly assumes trusted code; its normal composed-bundle route evaluates project dependency definitions and performs installation/update operations. This is a known policy conflict, not hypothetical generic risk. [Security model](https://shopify.github.io/ruby-lsp/security.html), [composition behavior](https://shopify.github.io/ruby-lsp/composed-bundle.html).

Move Ruby into the named first passive fixtures. Test a preassembled private custom bundle, disabled integrations, and dependency indexing from prepared data. Verify useful definitions/references alongside sentinels; an inert server with unresolved dependencies is not a success. The custom-bundle documentation itself warns about degraded discovery. Do not assume an existing lockfile makes Gemfile/gemspec evaluation inert. Keep the accepted runtime fleet unless an actual capability-equivalent simplification passes; replacing all semantic servers with parsers would violate scope.

### T3 — P2: Freeze the exact extraction topology before using parity or footprint claims

**Plan locations:** `planning/toolchain-proposal.md:147`, `planning/toolchain-proposal.md:250`, `planning/toolchain-proposal.md:252`, `planning/implementation-plan.md:91`, `planning/implementation-plan.md:115`.

The v2.51.1 docling.rs default uses a Rust renderer; PDFium is optional. Its tagged parity document reports **10/18 strict and 11/18 whitespace-normalized** matches using docling-parse rendering and **OCR disabled**, with remaining table/reading-order differences. These are upstream-reported results on that corpus, not Mirket measurements or proof of seven-language scan quality. The default-renderer configuration is different again. Correct the PDFium-default description and put renderer, model precision, OCR engine, fonts and thread budget in the test identity. [Tagged PDF conformance](https://github.com/docling-project/docling.rs/blob/v2.51.1/docs/PDF_CONFORMANCE.md), [CLI feature manifest](https://github.com/docling-project/docling.rs/blob/v2.51.1/crates/docling-cli/Cargo.toml).

For Python Docling, current 2.142.1 package metadata confirms that `docling` installs `docling-slim[standard]`, which includes more than this pipeline needs; `models-local` still includes Torch/torchvision. Its `models-onnxruntime` extra selects **onnxruntime-gpu on Windows**, so the name alone is not a CPU-only footprint reduction. The local TableFormer model package also retains Torch. Select reviewed individual extras and CPU artifacts; avoid automatic OCR selection, unnecessary OCR backends, chunking, speech, services and browser-render extras. [Docling metadata](https://pypi.org/pypi/docling/2.142.1/json), [slim extras](https://pypi.org/pypi/docling-slim/2.142.1/json), [model dependencies](https://pypi.org/pypi/docling-ibm-models/4.0.4/json).

**Recommendation:** make the already contemplated Docling/docling.rs comparison one bounded M0 experiment, rather than wait until the heavier baseline fails catastrophically. Keep both only in qualification fixtures; ship one. Promotion requires quality plus whole-closure savings on the three targets, not only the Mac condition currently stated at `toolchain-proposal.md:149`. Neither Rust nor ONNX alone establishes native Windows ARM64 portability.

### T4 — P2: Qualify the packaged library imports and browser inventory, not monorepo labels

**Plan locations:** `planning/implementation-plan.md:88`, `planning/implementation-plan.md:89`, `planning/implementation-plan.md:114`, `planning/toolchain-proposal.md:90`.

The intended narrow APIs are sensible, but their closures remain broader: OpenPencil CLI depends on its MCP package; core includes presentation/PDF export libraries. HyperFrames producer depends on studio-server and both `puppeteer`/`puppeteer-core`; producer and engine declare different compatible minimums. These are declared dependencies, not proof those services run. Inspect published npm artifacts and the actual resolved import graph before assuming tree shaking or a package name removes them. The existing Node runtime can execute published output; upstream Bun build scripts need not become an end-user runtime. [OpenPencil CLI/core](https://github.com/open-pencil/open-pencil/blob/v0.16.0/packages/cli/package.json), [HyperFrames producer](https://github.com/heygen-com/hyperframes/blob/v0.8.192/packages/producer/package.json), [engine](https://github.com/heygen-com/hyperframes/blob/v0.8.192/packages/engine/package.json).

Puppeteer ordinarily manages browser downloads/cache; modern Chrome and the old headless shell are distinct binaries. Prevent unintended downloads during controlled assembly, set explicit release paths, and count every browser/helper actually shipped. Sharing a Chromium **executable** does not require sharing browser sessions or profiles. Accept a dedicated render binary only after a concrete incompatible capture/media case; do not force a fragile override merely to claim deduplication. [Configuration](https://pptr.dev/guides/configuration), [supported browser mapping](https://pptr.dev/supported-browsers).

### T5 — P2: Add feature-level and assembly-level evidence to the first dependency inventory

**Plan locations:** `planning/implementation-plan.md:86`, `planning/implementation-plan.md:97`, `planning/implementation-plan.md:175`, `planning/implementation-plan.md:177`.

The plan correctly calls for exact pins and an upstream build-script allowlist. Make that inventory concrete at M0: **runtime files versus assembly-only tools; features/extras; models/fonts; native DLL/dylib dependencies; install/build download actions; compressed/installed/staging bytes per target**. Avoid postponing the first full-fleet size ledger until M5. One lockfile is desirable but does not prove all target-native optional packages are present: Sharp specifically documents cross-platform npm optional-dependency caveats. Assemble and verify target-specific closures from the lock/inventory without copying one machine's `node_modules`. [Sharp cross-platform instructions](https://sharp.pixelplumbing.com/install/).

FastEmbed 7.5.0's defaults include Hub downloading, ONNX binary downloading and image-model support. The manifest exposes a narrower ONNX/dynamic-loading route with local model loading; use a reviewed feature set with defaults disabled, a pinned compatible `ort`/ONNX pairing and release-owned library paths. Do not add Candle/Qwen/image features merely because the library supports them. Similarly, docling.rs's default CLI adds chunking/MCP: disable unwanted features rather than distribute another public server. [FastEmbed manifest](https://github.com/Anush008/fastembed-rs/blob/main/Cargo.toml), [docling.rs CLI features](https://github.com/docling-project/docling.rs/blob/v2.51.1/crates/docling-cli/Cargo.toml).

This is build/packaging work, not a recommendation for a new package manager, plugin architecture or runtime downloader. The accepted separate Python owners should remain; their ABI isolation is worth more than speculative deduplication.

### T6 — P2: Specify embedding-session eviction before adopting the idle-memory target

**Plan locations:** `planning/implementation-plan.md:62`, `planning/implementation-plan.md:76`, `planning/implementation-plan.md:128`, `planning/toolchain-proposal.md:397`.

Language-server and browser idle lifetimes are specified, but the model session's post-query lifetime is not. Two client-owned MCP processes may each retain an embedding model/session. “Starts only when needed” does not establish “releases memory after use.” Define bounded session reuse/eviction through existing lifecycle ownership, test simultaneous clients, and measure the cold-reload cost. This is an inference from the topology, not an observed leak or a reason to add a broker. Keep the 250 MiB idle figure explicitly provisional until both clients have exercised semantic recall and then become idle.

## Trends worth following, and claims not to import

- **Worth following: native language servers with an actual reduced runtime closure.** TypeScript's upstream native LSP is already selected appropriately. PHPantom is worth a focused comparison because it addresses a specific native-platform/runtime problem. Microsoft's new `roslyn-language-server` entry point is another upstream direction to watch, but its own installation example still uses prerelease packages; no evidence here shows it solves passive MSBuild loading or warrants replacing csharp-ls now. [Roslyn server README](https://github.com/dotnet/roslyn/blob/main/src/LanguageServer/roslyn-language-server/README.md).
- **Worth following: ONNX document pipelines with stage-specific evidence.** They can reduce an ML runtime closure, but default-renderer differences, quantization and OCR settings matter more than the implementation-language label. Keep Xberg as a secondary lead only if the first comparison fails; do not evaluate three broad frameworks simultaneously.
- **Worth following: embedded ANN once actual corpus scale requires it.** Vec1 is a credible SQLite-native development, but its current roadmap and scope-filter requirements do not justify replacing the simpler exact-search candidate before measurement. Avoid adding a vector service, graph memory system or second embedding framework.
- **Do not replace E5 simply because a newer model leads an aggregate leaderboard.** Qwen3-Embedding-0.6B is Apache-2.0 with multilingual/code retrieval and longer context, but is a larger model/inference choice; it is a second comparison only if reviewed English–Turkish queries expose a real E5 deficit. Jina v5-text-small is CC-BY-NC-4.0 with commercial licensing required; EmbeddingGemma uses Gemma-specific terms. These do not enter an OSS-qualified baseline merely because their weights are downloadable. [Qwen card](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B), [Jina license](https://huggingface.co/jinaai/jina-embeddings-v5-text-small), [EmbeddingGemma terms](https://huggingface.co/google/embeddinggemma-300m).
- **Do not reopen PhotoCraft or replace HyperFrames on activity/marketing alone.** Photo editing is not the missing interface-layout/image-conversion capability. HyperFrames remains a young but plausible HTML rendering owner; its exact offline Node/browser/media path needs proof, not another engine in reserve. No new evidence in this review warrants a second creative application stack.

## Minimum recommended plan changes

1. Correct the Phpactor native-Windows premise; qualify PHPantom 0.11.1 as the first replacement candidate, with no external execution/configuration bypass assumed.
2. Name Ruby and PHP in M0's passive analyzer gate; keep the existing Rust/C#/Java/Swift/framework cases and require useful navigation as well as absent side effects.
3. Correct docling.rs renderer facts and freeze comparison settings. Perform one bounded Docling/docling.rs comparison early; ship one winner and retain the accepted two-Python ownership where still needed.
4. Add per-target features/extras, assembly actions and footprint accounting to the first dependency batch. Prefer Tesseract CLI and minimal FastEmbed/Docling features. Qualify OpenPencil's published file imports and Chromium reuse before accepting extra runtime copies.
5. Specify embedding-session idle release and measure both clients after real recall. Keep all performance numbers provisional.

No broader stack replacement is justified by this review. No capability reduction, custom engine, global fallback, VM/container, runtime subscription/account, production dependency addition or implementation start is authorized by these recommendations.
